# Merge Request Workflow

먼저 [AI 협업 규칙](../rules/ai-collaboration.md)과 [Git 규칙](../rules/git.md)을 읽는다. 테스트를 실행한다면 [테스트 규칙](../rules/testing.md)도 읽는다.

## 실행 순서

1. Git 저장소 여부와 현재 Branch를 확인한다. 저장소가 없으면 초기화하지 않고 실행 불가 이유를 보고한다. 작업 트리의 미커밋 변경도 확인해 MR에 포함되는 변경과 구분한다.
2. Target Branch와 원격 저장소를 확인한다. 사용자 요청과 프로젝트의 확정된 설정을 우선한다. Target을 `main`, `master`, `develop` 등으로 추측해 확정하지 않는다. 결정할 근거가 없으면 확인을 요청한다. 로컬 원격 추적 정보의 최신 여부를 확인할 수 없으면 그 한계를 표시한다.
3. 확인된 Target 참조와 현재 Branch의 Commit 차이를 확인한다. `git log <target>..HEAD --oneline`으로 대상에 없는 Commit을 확인한다. `<target>`은 실제 확인한 참조로 대체하며 명령 예시를 그대로 실행하지 않는다.
4. `git diff <target>...HEAD`로 공통 조상 이후 현재 Branch의 전체 Diff를 읽고 변경 파일·추가·삭제·이름 변경을 확인한다. 참조나 공통 조상을 확인할 수 없으면 원인을 보고하고 비교를 완료했다고 표현하지 않는다.
5. 변경 목적과 기존 기능에 미치는 영향을 파악한다.
6. 주요 변경사항을 정리한다.
7. 중요한 구현 선택과 그 이유를 정리한다.
8. 실제 수행한 검증 내용과 결과를 정리한다. 기록의 출처를 구분하고 실행하지 않은 테스트를 수행했다고 작성하지 않는다.
9. 테스트하지 못한 부분과 기능 영향 확인이 필요한 부분을 표시한다.
10. 리뷰어가 집중해서 볼 부분을 정리한다.
11. 프로젝트 루트의 `.gitlab/merge_request_templates/Default.md`를 실제로 읽고 제목·본문 초안에 적용한다. 체크리스트는 확인된 항목만 체크한다.
12. 원격 MR 생성 또는 수정은 해당 작업에 대한 사용자의 명시적 요청이 있을 때만 실행한다. 저장소, Source/Target Branch, 제목·본문, 기존 MR 유무를 확인하고 이용 가능한 GitLab 도구로 수행한다. 새 MR이 필요한지 기존 MR 수정인지 구분한다. 원격 Branch가 없으면 필요한 Push를 별도 권한 기준에 따라 처리하며 자동으로 승인된 것으로 보지 않는다.

## 작성 원칙

MR은 단순 변경 파일 목록이 아니다. 왜 변경했는지, 무엇이 달라졌는지, 중요한 구현 선택, 검증 방법, 리뷰어가 확인할 부분을 설명한다. 특별한 판단이 없는 단순 변경의 구현 설명은 간결하게 작성한다.

MR 검토 준비 요청에 코드 리뷰까지 포함되어 있으면 [Code Review Workflow](code-review.md)를 추가로 읽고 수행한다.

## 결과 보고와 작업 경계

MR 본문 초안 작성과 실제 원격 생성·수정을 구분한다. 원격 작업을 수행했다면 도구 결과를 확인하고 MR 링크와 Source/Target Branch를 보고한다. 도구·인증·권한이 없거나 실행에 실패하면 작성한 초안과 구체적인 제한을 제공한다. MR 생성 후 자동으로 Merge하지 않는다.
