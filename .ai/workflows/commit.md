# Commit Workflow

먼저 [Git 규칙](../rules/git.md)을 읽는다. [AI 협업 규칙](../rules/ai-collaboration.md)은 아직 읽지 않았을 때만 읽는다. 테스트를 실행한다면 [테스트 규칙](../rules/testing.md)도 읽는다.

## 실행 순서

1. 프로젝트 루트와 Git 저장소 여부를 확인하고 `git branch --show-current`로 현재 Branch를 확인한다. 저장소가 없으면 초기화하지 말고 실행 불가 이유를 보고한다. Detached HEAD이면 상태를 설명하고 Commit 대상 의도를 확인한다.
2. `git status --short`로 수정·Staging·미추적 파일을 확인한다.
3. `git diff`로 Staging되지 않은 변경을 확인한다.
4. `git diff --staged`로 이미 Staging된 변경을 확인한다. 미추적 파일은 위 Diff에 나타나지 않으므로 포함 후보의 실제 내용도 별도로 읽는다.
5. 변경사항의 목적을 파악한다.
6. Commit에 포함할 파일과 변경 단위를 확인한다. 사용자 요청과 기존 Staging 상태를 함께 고려한다.
7. 관련 없는 변경이 섞였는지 검사한다. 기존 Staging 영역에 다른 사람의 작업이 있을 수 있으므로 임의로 해제하거나 함께 Commit하지 않는다. 분리할 범위가 불명확하면 먼저 확인한다.
8. 포함할 변경에 Secret 또는 Credential이 있는지 확인한다. 발견하면 민감한 값을 출력하지 말고 해당 변경의 Commit을 중단한 뒤 처리 방향을 보고한다. 육안 확인을 완전한 탐지로 표현하지 않는다.
9. Git 규칙을 적용하고 관련 검증의 실제 결과를 확인한다. 검증을 실행하지 못했다면 이유를 기록한다. 실패나 미검증을 숨기고 진행하지 않는다.
10. 실제 변경을 반영한 Commit Message를 생성한다.
11. 사용자가 실제 Commit을 요청한 경우에만 실행한다. 필요한 파일·변경만 명시적으로 Stage하고 `git diff --staged`를 다시 확인해 의도한 범위인지 점검한 후 Commit한다. 관련 없는 기존 Staging과 안전하게 분리할 수 없으면 실행 전에 확인한다. 변경이 없으면 빈 Commit을 만들지 않고 보고한다.
12. 결과를 보고한다. 초안만 작성했다면 실행하지 않았음을 표시한다. 실제 Commit했다면 Commit ID, 메시지, 포함한 변경, 검증 결과와 남은 변경을 확인해 보고한다. 실패했다면 실패 원인과 영향을 보고하고 성공으로 표현하지 않는다.

## 작업 경계

Commit Message 작성 요청과 실제 Commit 실행 요청을 구분한다. 관련 없는 파일을 한꺼번에 `git add`하지 않는다. 사용자가 별도로 요청하지 않은 Push는 하지 않는다. Hook 실패를 우회하거나 기존 이력을 변경하는 작업으로 자동 전환하지 않는다.
