# Jira Issue Workflow

먼저 [Jira 규칙](../rules/jira.md), [기준 문서](../references.md)를 읽는다. [AI 협업 규칙](../rules/ai-collaboration.md)은 아직 읽지 않았을 때만 읽는다.

## 실행 순서

1. 요청을 구분한다. 이슈 초안 작성, 실제 이슈 생성, 기존 이슈 수정, 상태 변경 중 무엇인지 확인한다. Jira 생성·수정은 외부 시스템 변경이므로 해당 작업을 명시적으로 요청받은 경우에만 실행한다.
2. 근거를 모은다. 기능 명세서에서 기능 ID, 담당, MVP 범위를 확인한다. 관련 API 명세와 ERD, 선행 이슈도 확인한다. 근거를 찾을 수 없는 내용은 추측해서 쓰지 않는다.
3. 중복을 검색한다. 프로젝트 키 `S15P31C106`에서 비슷한 제목, 같은 기능 ID, 같은 작업 내용을 검색한다. 비슷한 이슈가 있으면 새로 만들지 않고 보고한다.
4. 상위 에픽을 정한다. 프로젝트의 에픽 목록을 조회해 맞는 에픽을 고른다. 어느 에픽인지 불명확하면 확인을 요청한다.
5. 초안을 쓴다. [Jira 규칙](../rules/jira.md)의 유형, 제목 형식, 스토리포인트, 설명 순서를 따른다.
   - 5포인트를 넘는 작업은 나누는 안을 제시한다.
   - 여러 이슈를 만들면 담당자별 한 주 포인트 합계가 40을 넘지 않는지 확인한다.
   - 완료 기준은 체크박스로 쓰고, 이미 끝난 항목만 체크한다.
6. 보고자와 담당자를 확인한다. 자동값으로 두지 않는다. 확인할 수 없으면 비워 두고 보고한다.
7. 요청받은 경우에만 생성·수정한다. 설명의 체크박스와 목록은 처음부터 Jira 문서 형식(ADF)으로 저장한다. Markdown 체크박스는 `[ ]` 글자로 깨질 수 있다. 여러 이슈를 한꺼번에 만들 때는 초안 목록을 먼저 보여 주고 승인을 받는다.
8. 작성 후 다시 조회한다. 제목, 상위 에픽, 스토리포인트, 상태, 담당자, 보고자, 체크박스 형식을 확인한다. 다르게 저장되었으면 고치고 보고한다.
9. 결과를 보고한다. 이슈 키와 링크, 확인한 항목, 확인하지 못한 항목을 구분한다. 초안만 작성했다면 Jira에 반영하지 않았다고 표시한다.

## 작업 경계

상태는 사용자가 요청한 경우에만 바꾼다. 완료로 옮기는 것은 병합과 검증이 끝난 뒤다. 이슈 생성 요청은 Branch 생성이나 구현의 승인이 아니다. 구현까지 요청받았으면 [Implement Workflow](implement.md)를 이어서 따른다.
