# Agent 완료 시각 계산 (FN-AGT-09, Jira 148)

Agent가 "이 작업지시를 끝내려면 몇 시간 걸려?", "언제 끝나?"에 답할 때 쓰는 조회 도구 `ESTIMATE_COMPLETION`이다. 계산은 서버가 하고 AI는 결과를 받아 답만 쓴다. AI가 직접 곱하고 더하면 값이 틀릴 수 있기 때문이다. Action 정의서 7절의 "추가 제안" 도구를 구현했다.

## 계산 규칙

- 공정 하나의 소요 시간 = `남은 수량 × 개당 표준 가공 시간(초)` + `표준 준비 시간(분)`
  - 남은 수량은 작업지시 공정별 배정의 `remaining_qty`다.
  - 개당 표준 가공 시간·표준 준비 시간은 제품별 공정 표준(`std_cycle_sec`, `std_setup_min`)이다. 작업지시의 제품 코드와 공정 순서로 찾는다(재배정 검증과 같은 방식).
- `완료` 공정은 뺀다. 계산 순서상 맨 처음 공정이 `진행` 중이고 그 설비에서 이어서 하면 금형이 이미 걸려 있다고 보고 준비 시간을 넣지 않는다. 그 밖의 공정은 진행 중이어도 준비 시간을 넣는다(앞 공정이 금형을 바꾼다). 설비(`equipmentId`)를 정했는데 그 공정의 지금 설비 코드와 다르거나, 둘 중 하나를 볼 수 없으면 준비 시간을 넣는다(늦은 쪽). 볼 수 없어서 넣었으면 가정에 그렇게 적는다.
- 공정 순서(`operationSequences`)를 주면 그 공정만, 안 주면 끝나지 않은 공정 전체를 계산한다. 준 공정이 없거나 이미 끝났으면 남은 공정만 계산하지 않고 `missingInputs`로 알린다.
- 설비(`equipmentId`)를 주면 그 설비의 설비 종류(`kind`)와 공정 표준의 설비 종류(`equipment_kind`)가 같은 공정만 계산한다. "P101에서 찍으면"처럼 물을 때 프레스 공정(성형·트리밍)만 세고 검사는 빼기 위해서다. 설비 능력(톤수)과 가동 상태는 확인하지 않는다(재배정 검증이 본다).
- 받은 작업지시 순서, 공정 순서대로 쉬지 않고 이어서 한다고 본다(연속 가동). 작업지시마다 그때까지 누적한 완료 시각을 준다.
- 교대·휴무·비가동·작업 대기는 반영하지 않는다(2026-11-12 결정). 그래서 실제보다 이른 시각이 나온다. 답변에 이 가정을 함께 말한다.
- 시간은 소수 첫째 자리(반올림), 완료 시각은 초 단위(소수 초는 올림)다. 시각은 한국 시간 오프셋으로 준다.
- 납기와 비교한 판단은 하지 않는다(FN-AGT-07, Jira 259 보류).

## 입력

| 필드 | 필수 | 설명 |
|---|---|---|
| `workOrderIds` | 예 | 작업지시 객체 ID. 이어서 할 순서대로. 1~20개, 중복·빈 값 불가 |
| `operationSequences` | 아니오 | 계산할 공정 순서(예: `["20", "30"]`). 모든 작업지시에 같이 적용한다. `"20.0"`은 `"20"`으로 맞춘다 |
| `equipmentId` | 아니오 | 이 설비에서 한다고 볼 설비 객체 ID. 사용자가 설비를 말했을 때만 넣는다 |
| `startAt` | 아니오 | 계산 시작 시각(ISO-8601). 오프셋이 없으면 한국 시간. 없으면 현재 시각 |

입력이 잘못되면 계산하지 않고 실패(`error`)로 기록한다. 이번 답변의 대상이 아닌 작업지시나 설비가 하나라도 있으면 다른 객체 도구처럼 `NOT_TARGET`을 돌려주고 기록하지 않는다(147).

## 결과

| 경우 | resultCategory | data |
|---|---|---|
| 계산함 | `FOUND` | `estimatedCompletionAt`, `totalHours`, 작업지시·공정별 근거(`workOrders[]`), `equipment`(설비를 줬을 때), `assumptions` |
| 작업지시·설비가 없거나 볼 수 없음, 남은 공정이 없음, 요청한 공정이 없거나 끝남·설비 종류가 다름, 공정 상태·설비 종류·공정 표준·값이 없음 | `NO_DATA` | `missingInputs`에 이유. 완료 시각은 null |
| 공정·공정 표준(·설비) 유형이나 계산에 필요한 값을 볼 수 없음 | `DENIED` | `missingInputs`에 이유 |

- 볼 수 없는 유형의 작업지시는 있다는 사실도 알리지 않고 "찾을 수 없습니다"로 답한다(205).
- 설비 코드(공정의 배정 설비 코드, 설비 코드)는 준비 시간을 넣을지 정하는 데만 쓴다. 민감 값이면 DENIED로 막지 않고 비운 뒤 `restrictedPropertyCodes`(`유형코드.속성코드`)로 알리고, 준비 시간을 넣는다(늦은 쪽).
- 설비 이름은 객체 상세 조회(077)에서 받는다. 원본 표시 이름에는 민감 속성이나 원천 키(설비 코드)가 들어 있을 수 있어 205 기준으로 가린 표시 이름을 쓴다.
- 출처(`sources`)는 계산에 읽은 작업지시·공정·공정 표준 객체다. 기준 시점은 이 객체들의 원천 표 기준이다(145).
- `estimated`는 메모 추정 연결 표시라 이 도구에서는 늘 false다. 계산 가정은 `assumptions`로 따로 준다.

## 설정

`application.yml`의 `axcore.agent.completion-estimate.*`에 객체 유형·속성 코드(작업지시·공정·공정 표준·설비)와 완료·진행 상태 값을 둔다. 기본값은 시연 정답 온톨로지(`ai/data/gold-v1.0/ontology.json`)의 이름이다. 값이 빠지면 서버가 시작하지 않는다.

| S4 연속 가동: JB2610-0138(진행 중 2,400개) 뒤에 JB2610-0141 | 2,400 × 11.5초 + 30분(0138 30공정) + 3,200 × 11.5초 + 70분 | 10/31 09:33 |

P1은 `ai/data/gold-v1.0/scenario_answers.json`과 같다. S4의 정답 "연속 가동 가정 완료"(10/31 09:03)는 0138 30공정의 준비 시간을 넣지 않은 값이다. 이 도구는 맨 처음 공정만 준비 시간을 빼므로 30분 늦다. 정답의 교대 반영 일정도 0138 30공정에 준비 시간을 넣는다. 실제 GMS 모델로 P1을 돌린 결과는 `docs/agent-scenario-gms.md`의 2026-11-12 결과에 있다. 정답의 "교대 반영 일정"(10/31 15:34)은 교대를 반영하지 않으므로 이 도구로는 나오지 않는다.
