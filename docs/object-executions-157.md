# 객체 실행 이력 프론트 연동

- Jira: S15P31C106-157 · 기능: FN-EXP-03 · API: 080.
- 객체 상세의 `이 객체 실행 이력`에서 `/audit?objectId={id}`로 이동한다.
- 기존 조회·상세 화면에 페이지 이동을 추가했다. 객체 번호가 잘못된 주소는 오류를 표시하고 전체 이력 조회로 전환하지 않는다.

## 요청과 표시

`GET /api/v1/objects/{id}/executions`에 `from`, `to`, `status`, `page`, `size`를 보낸다. 첫 페이지는 0, 페이지 크기는 20이다. 종류·대상 조건은 객체별 API에 보내지 않는다.

시작일은 한국 시각 당일 0시, 종료일은 다음 날 0시를 UTC로 변환한다. 서버의 `from` 포함·`to` 미포함 계약에 맞춰 사용자가 고른 종료일까지 조회한다. 검색·초기화는 첫 페이지로 돌아간다.

응답의 `data`와 `meta.page`, `meta.size`, `meta.totalElements`로 목록과 페이지 이동을 표시한다. 같은 컴포넌트를 쓰는 전체 실행 이력(096)도 페이지를 전송하며 종류 변경 시 첫 페이지로 돌아간다.

객체를 바꾸면 페이지·검색 조건을 초기화한다. 진행 중인 조회에는 취소 신호를 전달하고, 다른 객체나 조건의 응답을 임시 데이터로 표시하지 않는다.

성공 결과, 차단 이유, 실패 이유, 변경 전후는 기존 상세 표시를 사용한다. `restrictedPropertyCodes`에 있는 null 값은 권한으로 가렸다고 표시한다. ADMIN의 전체 객체 이력과 다른 역할의 본인 실행 범위, 객체 조회 가능 여부는 서버가 결정한다.

401·403·404·409는 조회 실패로 표시한다. 서버·네트워크 오류는 동일한 조회를 재시도할 수 있다. 빈 목록은 오류와 별도로 표시한다. 이 화면은 조회만 하며 실행·상태 변경 요청을 보내지 않는다.

## 확인 근거와 검증 범위

- Jira 이슈와 저장소의 `ObjectExecutionController`, `ObjectExecutionSearchRequest`, `AuditExecutionResponse`, `AuditExecutionQueryService`, `AuditExecutionApiTests`를 대조했다.
- Notion의 기능 명세서와 API 관리 DB는 두 연결 계정 모두 404를 반환해 원문을 확인하지 못했다. API·DB 계약 변경은 없다.
- `api.test.ts`, `ObjectExecutionHistory.test.tsx`는 HTTP 모의 응답으로 요청 조건·페이지 이동·검색 초기화·객체 전환·권한 오류·재시도·상세 표시를 검증한다. 기존 Audit·Explorer·History 화면 테스트도 함께 실행한다.
- 개발 서버는 기존대로 MSW를 사용한다. 운영 빌드에서는 MSW를 시작하지 않고 공통 클라이언트가 같은 출처의 `/api/v1`을 호출한다. 실제 서버 세션과 데이터, 서버의 권한 통제는 이번 프론트 테스트로 검증하지 않는다.
- 팀원 리뷰·MR 병합 후 실제 서버에서 객체 선택 → 이력 조회 → 페이지 이동 → 상세 결과·실패 사유 확인이 남아 있다.
