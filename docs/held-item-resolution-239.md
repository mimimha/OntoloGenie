# S15P31C106-239 개별 보류 건 수동 처리

관리자 → 연결 규칙 → 제안 상세 → 규칙 이력 → 개별 보류 건 → 보류 건 상세.
기존 경로 `/admin/rules/{proposalId}/history?view=held`를 사용한다.
제안 전체의 검토 보류와 구분하며, 개별 보류 건의 수동 승인·종결만 다룬다.

## 현재 구현

- 기존 056 목록·057 상세 조회를 유지하고 상세에 수동 처리 화면을 추가한다.
- `HELD`만 처리 가능하며 `APPROVED`·`AUTO_RESOLVED`·`DISMISSED`·미지원 상태는 읽기 전용이다.
- 허용 동작·차단 사유, 사유 필수 여부·길이를 확정된 서버 근거로 전달받는 화면 전용 어댑터를 분리한다. 근거 없이 재검사 조건을 추정하거나 버튼을 활성화하지 않는다.
- 수동 승인은 양의 안전한 정수 대상 객체 ID가 필요하며 출발 객체와 같은 ID를 거절한다. 도착 객체 유형 등 업무 조건은 서버가 최종 검증해야 한다.
- 종결 입력에는 대상 객체 ID를 넣지 않는다. 입력 → 처리 내용 확인 → 최종 승인/종결로 나눈다. 입력 중 Enter는 실행하지 않는다.
- 실행 중 중복 클릭과 창 닫기를 막는다. 처리된 상세·목록은 서버 결과로 갱신하며 상태를 임의로 성공 처리하지 않는다.
- 처리 결과의 대상 건·상태·연결 ID·처리자·시각·감사 실행 ID를 확인한다. 정상 결과를 확인하지 못하면 응답 유실과 같이 취급하고 재실행 전에 최신 상태를 확인한다.
- 409·401·403·404 및 결과가 불확실한 실패는 재실행을 막고 최신 상세·정책 확인을 요구한다. 422 입력 오류는 입력을 수정할 수 있다. 변경 요청은 자동 재시도하지 않는다.
- 오래된 상세 캐시를 조회 중에는 처리 화면을 표시하지 않는다. 작성 중 폼이 백그라운드 조회로 사라지지 않도록 상세의 focus/reconnect 자동 재조회를 끈다.
- 원천 오류 원문을 새 처리 화면에 표시하지 않는다. 백엔드·DB·인증 구조 변경은 없다.

## 확인한 계약 및 미연결 범위

2026-11-07 [058 초안](https://app.notion.com/p/405bdf14d2d881dea3d4dda5b646c3f6)을 확인했다.
POST `/api/v1/held-items/{id}/resolution`, ADMIN 전용이다.
APPROVE는 targetObjectId 필수이며 수동 연결을 생성하고, DISMISS는 연결을 생성하지 않는다.
이미 처리된 건은 409, 부적합 대상은 422이며 상태·연결·감사를 한 트랜잭션으로 기록한다.
AUTO_RESOLVED는 수집에 의한 자동 처리 상태로 이 API의 결정값이 아니다.

운영 Swagger와 현재 HeldItemController에는 056·057 GET만 있으며 058 POST는 없다.
대응 BE S15P31C106-238(정유림)은 상태·재검사 정책 확정 후 적용하도록 되어 있다.
실제 `resolutionAccess`를 주입하지 않으므로 배포 후에도 수동 처리 버튼은 비활성화된다.
화면 테스트는 합성 데이터와 주입 함수를 사용하며 임의의 058 HTTP Mock 계약을 만들지 않는다.

## 후속 작업

1. 058 요청·응답 DTO, 사유 필수/길이, 재검사·상태·허용 동작 근거 제공 방식 및 처리 정책을 담당자와 확정한다.
2. `HeldResolutionAccess`로 변환하는 실제 어댑터를 작성하고 `HeldItems`에 주입한다. `availability`는 화면 경계이며 새로운 HTTP 엔드포인트를 가정하지 않는다.
3. 승인 대상 탐색/선택 방식과 도착 유형·권한·동시 처리 검증을 확인한다. 현재 화면은 대상 객체 ID 입력을 제공한다.
4. 실제 API로 승인·종결, 처리 이력·감사, 중복·충돌·재검사 차단, 트랜잭션 실패 시 연결/상태/감사 롤백을 검증한다.
5. 팀원 리뷰·MR 병합·병합 후 검증을 완료한다. 실제 API 연결·운영 검증 전에는 Jira 완료로 옮기지 않는다.
