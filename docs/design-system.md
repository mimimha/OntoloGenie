# OntoloGenie UI/UX 디자인 시스템

정보가 많은 업무 화면에서 필요한 정보를 빠르게 찾고, 비교하고, 판단하기 위한 기준이다. **1절은 사용자 확정 방향**, 나머지 크기·배치·동작 세부사항은 구현 기준이다. 기존 배포 관찰은 2절, 현재 코드 적용 범위는 11절에서 구분한다.

## 1. 확정된 방향

- **가독성 우선:** 라프텔의 시각 언어를 참고하되 업무 정보의 탐색·비교·판단에 맞게 적용한다.
- **라이트 테마:** 대표 키컬러 `#8975F6`와 기존 보라색 계열을 유지한다. 다크 테마·테마 전환은 이번 범위에 포함하지 않는다.
- **흰색 전체 배경:** 페이지 전체 바탕은 `#FFFFFF`로 한다. 회색은 표 헤더·관계도·비활성 입력·hover 등 영역이나 상태 구분이 필요한 곳에만 제한적으로 사용한다.
- **기본형 밀도:** 관련 항목은 가까이 묶고 다른 정보 그룹은 구분한다. 여백을 화면 전체에 일괄 늘리거나 별도 밀집 모드를 추가하지 않는다.
- **상세 조회:** 우측 패널을 기본으로 하고 복잡한 편집은 별도 페이지로 구성한다.
- **데스크톱 중심:** 모바일 전용 UX·모바일 전체 업무 지원을 별도 목표로 두지 않는다.
- **페이지네이션:** 사용자가 제공한 Bolt 예제의 처음·이전·페이지 번호·다음·마지막 구성을 사용한다.

참고 자료는 사용자 첨부 `라프텔 — design.md`(2026-11-09)다. CSS·렌더링 분석 자료이며 라프텔 팀의 공식 발행·승인 여부는 미확인이다. GetDesign 최신 본문은 직접 확인하지 못했다. 원본 관찰값을 프로젝트의 확정 토큰이나 구현 완료 상태로 취급하지 않는다.

## 2. 배포 화면 검토 — 2026-11-12

사용자가 로그인한 관리자 세션에서 **업무 데이터·AI 업무 도우미·데이터 연결·연결 규칙·Action 정의·실행 이력·정의·규칙 이력·계정·권한의 8개 화면**을 확인했다. 메뉴 이동·객체 선택·조회 탭 전환과 화면 캡처·일부 계산 스타일을 확인했다.

주 검토 크기는 **1440×900**, 업무 데이터 전체 구조는 **1280×900**에서도 확인했다. 다음은 당시 배포 상태의 관찰이며, 적용할 개선 기준은 이후 절에서 정의한다.

| 우선순위 | 영역 | 관찰 결과 |
| --- | --- | --- |
| 높음 | 페이지 제목 | 여러 화면에서 본문 페이지명이 드러나지 않는다. 실행 이력 H1은 absolute 배치·1×1px로 확인했다 |
| 높음 | 전체 관계도 | 전체 구조의 노드명·관계명·건수가 작게 축소돼 최초 화면에서 읽기 어렵다 |
| 높음 | 객체 상세 | 1440px에서 관계도·연관 목록 아래로 길게 이어지고 큰 어두운 면으로 표시된다 |
| 높음 | 표·보조 정보 | 헤더·설명·출처 안내가 작고 옅다. 실행 이력 표 헤더는 12px·`rgb(139, 141, 154)`였다 |
| 중간 | 업무 데이터 검색 | 속성 조건·값 입력이 비활성이고 내부 구현 상황을 설명하는 placeholder가 보인다 |
| 중간 | 객체·규칙 목록 | 반복 카드·배지·여백이 크고 목록 내부 스크롤과 페이지 이동이 함께 존재한다 |
| 중간 | 연결 규칙 | 상태·유형·검색·상세 필터가 여러 줄로 쌓인다. 상세에서는 큰 신뢰도 수치와 반복 상태 문구가 눈에 띈다 |
| 중간 | AI 업무 도우미 | 문단·목록·강조 구조와 16px / 26px 본문은 유지할 만하다. 접힌 출처·조회 상태 안내는 옅게 보인다 |
| 중간 | Action 정의 | Agent 사용 사유의 동일한 설명이 여러 행에서 반복된다 |
| 중간 | 데이터 연결·이력 | 서로 다른 의미의 시각·상태 설명이 작은 글자와 긴 문장에 섞여 있다 |
| 중간 | 페이지네이션 | 이전·다음과 현재/전체 안내만 있으며 처음·마지막·주변 번호 이동은 없다 |
| 중간 | 배경·탐색 | 큰 모서리·그라데이션·반투명 면이 반복된다. 규칙 화면에서는 공통 헤더의 정의·규칙 이력 링크가 보이지 않는다 |

**별도 기능 점검:** 정의·규칙 이력의 ‘정의 변경’ 탭은 로딩 후 `대상을 찾을 수 없습니다` 오류를 표시했다. ‘규칙 개정’은 검색 전 안내까지 확인했다. 정의 변경의 정상 목록과 오류 원인은 미확인이다.

**검토 범위:** 관리자 한 역할, 한 개 설비 선택과 기존 AI 대화 사례를 확인했다. 새 질문·생성·수정·삭제·승인·실행은 수행하지 않았다. 다른 역할, 1920px, 200% 확대, 키보드 전체 탐색·스크린리더·전체 대비·모든 상세/편집/다이얼로그·실패 조합은 검증하지 않았다. 이는 시각 검토이며 전체 기능·접근성 테스트 통과를 뜻하지 않는다.

## 3. 정보 구조와 읽기 흐름

화면 설계 시 `사용자가 할 판단 → 목록에서 비교할 필드 → 상세에서 확인할 필드 → 항상 보여야 할 주의 상태`를 먼저 정한다. 구체적인 필드는 기존 기능 명세와 실제 업무 흐름을 따른다.

| 정보 역할 | 배치 |
| --- | --- |
| 항목 식별 | 목록 앞부분과 상세 상단의 이름·ID |
| 비교·판단 | 목록의 핵심 열과 상세 요약의 상태·값·단위 |
| 즉시 주의 | 오류·승인 필요·실행 실패·차단 사유를 목록·요약에서 인지 가능하게 표시 |
| 전체 속성·설명 | 상세의 정렬된 속성 행과 긴 설명 본문 |
| 관계·근거·이력 | 이름 있는 섹션으로 구분하고 긴 내용은 단계적으로 펼침 |

### 공통 페이지

```text
페이지 제목 · 짧은 설명                         주요 행동
검색 / 필터                                      검색 · 초기화
적용 조건 · 결과 수
표 / 목록 / 관계도                              우측 상세
페이지네이션
```

- 대표 제목은 본문에서도 보이게 한다. 메뉴 선택 표시나 접근성 트리에만 있는 제목으로 대신하지 않는다.
- 같은 역할·권한에서 메뉴의 위치·명칭·발견 가능성을 통일한다. 규칙 화면의 이력 링크 차이는 실제 권한 정책을 확인한다.
- 결과 수는 한 곳을 기본으로 표시한다. 필요해 상·하단에 함께 표시하면 같은 값과 용어를 사용한다.
- 편집 화면은 제목 → 폼 → 저장·취소, AI 화면은 대화 목록 → 대화·근거 → 입력의 구조로 조정한다.
- 고정 헤더·하단 작업 바와 내부 스크롤이 내용·키보드 포커스를 가리지 않게 한다.

### 우측 상세

- 상단에는 선택 대상의 이름·ID·핵심 상태·필요한 행동을 배치한다.
- 본문은 기본 정보·관계·근거·이력으로 나눈다. 실제 순서와 제공 항목은 업무 흐름에 맞춘다.
- 짧은 속성은 라벨·값이 정렬된 행, 긴 설명은 읽기 폭을 확보한 본문으로 구성한다.
- 필수 경고는 펼치기 안에만 두지 않는다. 추가 속성·긴 이력은 이름 있는 섹션으로 연결한다.
- 목록·관계도·상세를 함께 읽기 어려우면 목록/관계도 전환이나 상세 확장을 검토한다. 글자를 줄이거나 중요한 값을 일괄 말줄임하지 않으며 선택 대상·검색 맥락을 유지한다.

## 4. 색상

아래 토큰은 구현 제안이다. 코드에는 화면별 리터럴과 CSS 덮어쓰기가 분산돼 있어 공통 토큰으로 정리해야 한다.

### 키컬러

| 토큰 | 값 | 역할 |
| --- | --- | --- |
| `brand-primary` | `#8975F6` | 선택·진행·포커스 |
| `brand-strong` | `#6F5ADF` | 주요 버튼 면 |
| `brand-text-light` | `#6F5ADF` | 작은 활성 링크·텍스트 |
| `brand-legacy` | `#8065D8` | 기존 보조 포인트. 작은 글자에는 자동 재사용하지 않음 |
| `brand-subtle` | `rgb(137 117 246 / 10%)` | 선택 배경 보조 |
| `on-brand` | `#FFFFFF` | `brand-strong` 위 글자 |
| `on-brand-primary` | `#121212` | `brand-primary` 위 작은 글자 |

기존 버튼 그라데이션은 단색 면으로 정리하고, 원본의 보라 틴트 대신 프로젝트 키컬러에서 보조 면을 파생한다.

### 중립·상태 색

| 토큰 | 값 | 역할 |
| --- | --- | --- |
| `background-1` | `#FFFFFF` | 페이지 전체 바탕·패널·표·다이얼로그 |
| `background-2` | `#F7F7F7` | 표 헤더·관계도·비활성 입력·hover 등 국소 구분 면 |
| `background-3` | `#EEEEEE` | 보조 면·hover |
| `background-4` | `#E2E2E2` | 강한 중립 구분 면 |
| `foreground-1` | `#121212` | 제목·본문·필드 라벨 |
| `foreground-2` | `#505050` | 설명·보조 본문·중요한 placeholder |
| `foreground-3` | `#8A8A8A` | 낮은 중요도의 보조 표현 후보 |
| `foreground-4` | `#D0D0D0` | 비활성 표현 후보 |
| `border-1` | `#EEEEEE` | 일반 구분선 |
| `border-2` | `#E2E2E2` | 강조 구분선 |

- 페이지 전체와 기본 데이터 면은 불투명한 흰색을 사용한다. 영역은 여백·제목·구분선으로 먼저 나누고, 추가 구분이 필요한 부분에만 회색 면을 쓴다. 전체 바탕을 회색이나 장식용 그라데이션으로 채우지 않는다.
- 구현 토큰은 `--ui-canvas: #FFFFFF`, `--ui-surface: #FFFFFF`, `--ui-surface-subtle: #F7F7F7`로 구분한다. 국소 회색 면은 `--ui-surface-subtle`을 사용하며 키컬러와 선택 상태의 보라색 표현은 유지한다.
- 중요한 설명·상태명을 옅은 회색으로 낮추지 않는다. 입력 경계는 옅은 구분선과 구분해 `#8A8A8A`를 후보로 검토한다.
- 선택은 배경색과 선·체크·테두리를 병행한다. 색만으로 상태를 전달하지 않는다.
- 기존 `StatusBadge`의 neutral·info·success·warning·danger 의미와 slate·blue·emerald·amber·red 계열을 유지한다. 업무 상태를 모두 보라색으로 표시하지 않는다.

### 대비

| 단색 조합 | 계산 대비율 | 판단 |
| --- | --- | --- |
| 흰 글자 / `#8975F6` | 약 3.54:1 | 일반 글자 기준 미달 |
| `#121212` 글자 / `#8975F6` | 약 5.30:1 | 현재 번호·선택 칩 후보 |
| 흰 글자 / `#6F5ADF` | 약 5.00:1 | 주요 버튼 후보 |
| `#8065D8` 글자 / 흰 면 | 약 4.40:1 | 작은 링크에 그대로 사용하지 않음 |

목표는 일반 글자 4.5:1, 큰 글자 3:1, 필요한 조작 경계·상태 표시 3:1이다. 위 수치는 불투명 sRGB 단색 계산이며 실제 배경·반투명·상태별 대비는 구현 후 확인한다.

## 5. 타이포그래피

서체는 `Pretendard, 'Noto Sans KR', sans-serif`를 제안한다. 실제 폰트 파일·로딩 방식은 구현 시 확인한다.

| 토큰 | 크기 / 행간 | 굵기 | 역할 |
| --- | --- | --- | --- |
| `heading-32` | 32px / 48px | 700 | 페이지 제목 |
| `heading-24` | 24px / 36px | 700 | 주요 패널·다이얼로그 제목 |
| `title-16` | 16px / 24px | 700 | 섹션 제목 |
| `body-18` | 18px / 27px | 500 | 강조 설명 |
| `body-16` | 16px / 24px | 400 | 일반 설명 |
| `body-long-16` | 16px / 26px | 400 | 긴 상세·AI 답변 |
| `body-14` | 14px / 21px | 400 | 표·목록·짧은 속성 값 |
| `label-14` | 14px / 21px | 500 | 일반 라벨 |
| `control-14` | 14px / 21px | 600 | 메뉴·버튼·표 헤더·강조 라벨 |
| `input-14` | 14px / 21px | 400 | 입력. 필요한 경우 500 |
| `caption-12` | 12px / 18px | 500 | 부가 메타 정보. 짧은 배지는 600 후보 |

원본의 라벨 700·입력 600·caption 700을 위 기준으로 낮추고 제목·핵심 값에 강조를 집중한다. 정보량에 맞춰 본문을 일괄 축소하지 않으며 중요한 경고·승인 안내를 caption으로 처리하지 않는다. AI 답변은 배포에서 확인한 16px / 26px을 유지하는 방향이다.

## 6. 간격·모서리·깊이

| 간격 토큰 | 값 | 사용처 |
| --- | --- | --- |
| `space-8` | 8px | 아이콘·밀접한 항목·라벨과 입력 |
| `space-12` | 12px | 관련 항목·컨트롤 내부 |
| `space-16` | 16px | 필드 간격·일반 패널 내부·결과 요약과 콘텐츠 |
| `space-24` | 24px | 다른 정보 그룹·패널 사이·페이지 바깥 여백 |
| `space-40` | 40px | 큰 섹션 사이 |

반복 속성은 정렬된 행과 구분선으로 묶는다. 개별 항목마다 큰 카드와 24px 여백을 반복하지 않는다. 좁은 창의 바깥 여백은 16px을 후보로 삼는다.

| 모서리 토큰 | 값 | 사용처 |
| --- | --- | --- |
| `radius-xs` | 3px | 작은 배지 |
| `radius-sm` | 4px | 버튼·입력·일반 카드·표 |
| `radius-md` | 8px | 큰 패널·다이얼로그 |
| `radius-lg` | 16px | 진행바 |
| `radius-pill` | 9999px | 필터·상태 칩 |
| 원형 | 50% | 아이콘 버튼 |

고정 패널은 면과 1px 보더로 구분하고 일반 카드·버튼에는 상시 그림자를 두지 않는다. 드롭다운은 원본 라이트의 `0 0 16px`, 검정 25% 그림자를 출발점으로 검토한다. 다이얼로그는 오버레이로 구분한다. 수치는 대표 업무·AI 화면에서 검토하며 원본의 공식 토큰으로 취급하지 않는다.

## 7. 공통 컴포넌트

| 컴포넌트 | 표현·역할 |
| --- | --- |
| Header | 높이 64px 기준, 중립 면·하단 보더. 메뉴가 넘치면 높이 확장 |
| Nav / Tab | `control-14`, 활성 글자는 `brand-text-light`와 비색상 표시 병행 |
| Input | 높이 40px 기준, radius 4px, 좌우 12~16px. 검색은 상시 노출 |
| Primary Button | 높이 40px 기준, radius 4px, `brand-strong` + 흰 글자 |
| Secondary Button | 중립 면·보더·`foreground-2`. 취소·닫기·초기화 |
| Text / Icon Button | 상세·복사 등 낮은 우선순위 행동. 접근 가능한 이름 제공 |
| Danger Button | 기존 danger 계열. 실제 결과에 따라 삭제·되돌릴 수 없는 실행 구분 |
| Filter Chip | 높이 36px 기준, pill, 좌우 12px. 선택 시 `brand-primary` + `on-brand-primary` |
| Status Badge | 짧은 상태명, caption·pill. 내용·확대에 따라 높이 확장 |
| Card / Panel | 일반 카드 radius 4px·큰 패널 8px, 내부 16~24px |
| Dialog | radius 8px, 내부 24px. 기존 focus trap·Esc·포커스 복귀 유지 |

- 같은 작업 영역에서는 대표 행동 하나를 우선 강조한다. 검색과 편집처럼 영역이 나뉘면 각각 주요 행동을 둘 수 있다.
- 위험 행동은 대상·영향·구체적인 동사를 표시한다. 반려를 삭제와 같은 위험도로 일괄 취급하지 않는다.
- 기본·hover·focus-visible·selected·disabled·pending을 구분한다. hover·pressed에서도 글자 대비를 유지한다.
- 포커스 링은 키컬러 2px·offset 3px을 후보로 확인한다. pending은 진행 표시·`aria-busy`와 중복 제출 방지를 제공한다.

### 표·목록

- 기본 표는 `body-14`, 헤더는 `control-14`. 행은 최소 높이 44px, 셀 좌우 16px·상하 12px을 출발점으로 삼고 내용에 따라 확장한다.
- 이름·상태·날짜는 좌측, 수치·수량은 우측에 정렬한다. 단위·표시 정밀도를 통일하고 도메인 명세 없이 반올림하지 않는다. ID를 숫자 형식으로 변환하지 않는다.
- 미제공은 `—`, 실제 0은 `0`으로 구분한다. 미제공·알 수 없음·조회 실패의 의미를 혼동시키지 않는다.
- 날짜는 `YYYY-MM-DD`, 시각은 `YYYY-MM-DD HH:mm:ss`를 후보로 삼고 시간대를 표시한다. 수집·반영·실행 시각의 의미를 보존한다.
- 반복 설명은 공통 안내로 묶고 항목별 예외·차단 사유는 유지한다. 긴 값은 줄바꿈·원문 확인·명시적 복사 경로를 제공하며 hover에만 숨기지 않는다.
- 긴 표는 헤더, 넓은 표는 핵심 식별 열의 고정을 검토한다. 고정 영역은 불투명하게 하고 내부 가로 스크롤·포커스를 가리지 않는다.
- 선택 행과 hover를 구분한다. 정렬 기능이 있으면 방향과 `aria-sort`를 제공하고 행 클릭과 내부 버튼이 충돌하지 않게 한다.
- 목록 내부 스크롤을 사용하면 헤더·결과 수·페이지 이동의 위치를 명확히 한다.

### 폼·검색

- label → 입력 → 도움말/오류 순서로 배치하고 필수 여부를 알린다. placeholder를 label 대신 쓰지 않는다.
- 비활성 조건은 사용자 언어로 사유와 대체 검색법을 안내한다. 내부 구현 상황을 노출하거나 미지원 기능을 활성화하지 않는다.
- 검색 버튼·Enter로 적용하는 방식을 기본 후보로 삼는다. 기존 즉시 적용 필터는 기존 동작을 확인해 구분한다.
- 입력 중 조건과 적용된 조건을 구분한다. **새 조건을 실제 적용할 때** 첫 페이지로 초기화하고, 입력만 바꾼 상태에서는 기존 결과·페이지를 유지한다.
- 초기화는 해당 검색 영역의 조건을 대상으로 하며 목록 새로고침은 적용 조건을 유지한다. 적용 조건·결과 수를 함께 알린다.
- 검색 전·데이터 없음·결과 없음·실패를 구분한다. 필드 오류는 입력 아래에 두고 `aria-invalid`·설명 연결을 제공한다. 제출 실패 후 입력값을 유지한다.
- 미저장 이탈 경고·조건 URL 저장 등 신규 동작은 기존 정책 확인 후 별도 범위로 다룬다.

## 8. 페이지네이션

사용자 제공 [Bolt Pagination](https://boltdesignsystem.com/pattern-lab/patterns/40-components-pagination/index.html)의 구조를 React의 기존 `Pagination.tsx`에 적용한다. Twig 실행 환경·Bolt 패키지 추가를 전제로 하지 않는다.

### 사용자 제공 예제

```twig
{% include '@bolt-components-pagination/pagination.twig' with {
  current: 5,
  total: 10,
  first: {
    href: 'page-1-url'
  },
  previous: {
    href: 'page-4-url'
  },
  pages: {
    3: {
      href: 'page-3-url'
    },
    4: {
      href: 'page-4-url'
    },
    5: {
      href: 'page-5-url'
    },
    6: {
      href: 'page-6-url'
    },
    7: {
      href: 'page-7-url'
    }
  },
  next: {
    href: 'page-6-url'
  },
  last: {
    href: 'page-10-url'
  }
} only %}
```

### 표시·동작

```text
처음  이전  3  4  [5]  6  7  다음  마지막
```

- 예제는 현재 5쪽·전체 10쪽이다. `total`은 건수가 아닌 페이지 수이며 예제 번호·URL을 고정값으로 구현하지 않는다.
- 현재 주변 번호를 최대 5개 표시하고 경계에서는 범위를 이동한다. 1쪽은 `1 2 3 4 5`, 10쪽은 `6 7 8 9 10`이며 전체가 5쪽 이하면 모두 표시한다.
- 첫 페이지는 처음·이전, 마지막 페이지는 다음·마지막을 비활성화한다. 현재 번호는 같은 조회를 반복하지 않게 한다.
- 0건은 이동 컨트롤을 숨기고 빈 결과·건수를 표시한다. 1쪽만 있으면 번호 1을 현재 상태로 두고 이동 컨트롤을 비활성화한다.
- 조회 중 중복 이동을 막는다. 새 조건의 적용은 7절을 따르고, 데이터 변경으로 페이지가 사라지면 유효 범위로 보정한다.
- 번호 그룹과 전체 건수 안내를 분리하되 건수는 3절의 표시 원칙을 따른다. 페이지 크기 변경 UI는 추가하지 않는다.

### 스타일·연결

가운데 정렬, 간격 8px, 높이·번호 최소 너비 40px, radius 4px, 텍스트 버튼 좌우 12px을 후보로 삼는다. 현재 번호는 `brand-primary` + `on-brand-primary`, 나머지는 중립 면을 사용한다.

`nav aria-label="페이지 이동"`, 현재 번호의 `aria-current="page"`, 번호별 이동 이름을 제공한다. 좁은 창에서는 줄바꿈으로 조작에 접근하게 한다. 기존 36px 원형 버튼 스타일은 새 규격과 함께 정리한다.

| 예제·동작 | 기존 React 연결 |
| --- | --- |
| `current` | `page + 1` |
| `total` | `Math.ceil(totalElements / size)`. `size > 0`, 0건은 별도 처리 |
| 처음 / 마지막 | `onChange(0)` / `onChange(totalPages - 1)` |
| 이전 / 다음 | `onChange(page - 1)` / `onChange(page + 1)` |
| 표시 번호 `n` | `onChange(n - 1)` |

`page`·`onChange`는 0부터 시작한다. 범위 밖 이동·현재 번호 재선택·0건에서는 이동 콜백을 실행하지 않는다. 기존 버튼·콜백 조회 방식을 유지하고 URL 이동은 별도 요구가 있을 때 검토한다.

## 9. 업무 전용 표현과 피드백

### 관계도

- 객체 관계도의 주변 유형명과 중앙 객체명·유형명은 노드 폭 안에서 줄바꿈한다. 공백 없는 긴 영문 이름도 `overflow-wrap: anywhere`로 줄바꿈하며 원문을 잘라 숨기거나 글자 크기를 줄이지 않는다.
- 개요와 선택 대상의 읽기 상태를 구분한다. 전체 맞춤으로 글자가 작아져도 확대·선택·상세를 통해 전체 이름·방향·건수를 확인할 수 있게 한다.
- 기본·선택·포커스·연관 노드와 연결선을 구분하고 범례를 제공한다. 기존 관계 유형 색과 사용자 선택 색이 혼동되지 않게 한다.
- 확대·축소·화면 맞춤·선택 해제의 위치와 이름을 통일하고 목록·상세의 선택을 연결한다. 필수 정보는 관계도에만 의존하지 않는다.

### 비교·검토·AI

- 변경 전/후를 같은 속성 순서로 비교하고 추가·수정·삭제를 색과 라벨로 구분한다.
- 검토·반영·검사 상태와 다음 행동을 먼저 요약한다. 신뢰도는 보조 근거이며 승인·적용 성공을 뜻하지 않는다.
- AI 질문·답변·근거·제안·실행 결과를 구분한다. 출처·조회 상태는 발견 가능한 요약과 펼칠 수 있는 상세로 나눈다.
- 생성 중·근거 없음·확인 필요·실행 대기·처리 중·성공·실패는 실제 응답 기준으로 표시한다. 제공되지 않은 근거·진행률·비교 값을 만들어 표시하지 않는다.

AI 업무 도우미에서는 다음 기준을 적용한다.

- 대화 목록과 현재 대화를 나누고, 긴 대화 제목은 목록에서 두 줄까지·현재 대화 상단에서 전체를 확인한다. 선택은 보라색 보조 면과 왼쪽 선으로 표시한다.
- 질문·답변은 16px / 26px, 답변 읽기 폭은 최대 880px로 제한한다. 마크다운 제목·문단·목록의 간격을 구분하고 표·긴 코드는 각 영역 안에서 스크롤한다.
- 출처·조회 상태는 14px 요약과 펼칠 수 있는 표로 제공한다. 권한 제한·미확인·미연결·추정 건수는 응답에 있는 값으로 계산해 접힌 요약에서도 표시한다. 실행 결과는 별도 영역에서 실제 상태 문구와 상태 색을 함께 사용한다.
- 대화 내역만 스크롤하고 입력란은 유지한다. 이전 답변을 읽는 중에는 새 응답이 와도 강제로 맨 아래로 이동시키지 않는다. 대화 내용·표·코드 영역은 키보드로도 접근한다.
- 질문 라벨·입력 한도·Enter 및 Shift+Enter 사용법을 항상 확인할 수 있게 한다. 추천 질문과 내 질문은 입력란만 채우며, 전송은 사용자가 결정한다. 저장·전송 실패 시 입력과 지속 오류 안내를 유지한다.

### 피드백·문구

| 상황 | 표현 |
| --- | --- |
| 필드 오류 | 해당 입력 아래 오류와 필요한 폼 요약 |
| 저장 성공 | 짧은 비차단 알림과 갱신된 화면 상태 |
| 저장 실패 | 폼 내 지속 오류·입력 유지·다음 행동 |
| 조회 중 | 결과 영역 로딩. 이전 결과 유지 시 갱신 중임을 표시 |
| 장시간 실행 | 대상·진행 상태를 지속 표시. 실제 진행률이 없으면 백분율을 만들지 않음 |
| 실행 완료·실패 | 대상·결과·사유·근거 또는 이력 경로 |

버튼은 검색·저장·승인·취소처럼 동작을 직접 표현한다. 토스트만으로 필수 오류·승인 요청·장시간 작업 결과를 전달하지 않는다. 조회 재시도와 저장·실행 재요청을 구분하며, 상태가 불명확한 실행을 실패로 단정하거나 자동 재실행하지 않는다.

## 10. 데스크톱 배치와 접근성

- 대표 시안은 1440px, 창 너비 검토는 1280px·1920px을 후보로 삼는다. 이는 최소 지원 해상도나 새 breakpoint 확정이 아니다.
- 넓은 화면도 각 영역의 읽기 폭이 확보될 때 분할한다. 좁은 창·확대에서는 폼 줄바꿈·패널 재배치·영역별 스크롤로 접근을 유지한다.
- 기존 기능을 제거하거나 모바일 접속을 차단하지 않는다. 데스크톱 중심 범위 안에서 내용·조작의 잘림을 방지한다.
- 브라우저 줌과 reduced-motion 대응을 유지한다. 키보드로 메뉴·검색·표 행동·다이얼로그를 조작하고 이동·조회 후 포커스를 잃지 않게 한다.
- 기존 label·오류 연결·ARIA 의미를 보존하고 상태 변화는 보조 기술에 알린다. 같은 내용을 반복 낭독하거나 포커스 링을 일괄 제거하지 않는다.

## 11. 적용 순서와 완료 기준

1. 대표 업무의 목록 비교 필드·상세 필드·주의 상태를 정리한다.
2. 공통 토큰·폰트 로딩과 컴포넌트를 정리하고 업무 데이터 화면의 기준 시안을 검토한다.
3. 관계도·AI·검토 표현을 적용한 뒤 관리자·이력·로그인 화면에 확장한다.
4. CSS·Tailwind 덮어쓰기를 정리하고 개선 전후의 같은 업무를 비교한다.

스타일 진입점 `frontend/src/index.css`, 공통 `components/workspace.css`, 규칙 `features/review/rules.css`, 로그인 `features/auth/login.css`의 적용 우선순위를 함께 확인한다. `:has()`·클래스명 선택자·인라인·그래프 색도 점검한다.

기존 API 계약·권한·승인·업무 동작을 유지한다. 새 기능·의존성·API 변경은 프로젝트 규칙에 따라 별도 범위로 다룬다.

### 1차 적용 범위 — 2026-11-12

공통 헤더·메뉴·색상 및 타이포 토큰·버튼·입력·표·상태 배지·피드백·다이얼로그·Bolt 방식 페이지네이션과 **업무 데이터 화면**에 적용했다. 업무 데이터는 검색 조건 요약, 목록·관계도·우측 상세, 관계도 확장·유형 목록·배율 조절을 제공한다. 공통 스타일을 덮어쓰던 이전 CSS를 함께 정리했다.

공통 스타일은 이를 사용하는 다른 화면에도 반영된다. 로컬 모의 데이터로 960·1280·1440·1920px 창과 상세 모달의 Escape·포커스 복원을 확인했다. 실제 운영 데이터의 긴 값과 상태별 대조, 브라우저 200% 확대, 별도 웹폰트 로딩은 추가 확인 대상이다. 운영 배포는 수행하지 않았다. 구현 파일과 검증 방법은 [프론트엔드 README](../frontend/README.md#uiux-1차-적용)를 참고한다.

### 2차 적용 범위 — AI 업무 도우미

AI 업무 도우미에 보이는 페이지 제목, 흰색 패널·공통 토큰, 대화 목록·답변·입력 영역, 근거 요약·상세 표, 실행 결과 상태 구분을 적용했다. 기존 AI 화면을 간접 선택자로 덮어쓰던 CSS를 제거하고 `features/agent/agent.css`에서 관리한다. 질문 전송·한글 조합·추천 및 내 질문·첫 질문의 참고 객체·폴링·이전 대화 읽기·계획 상세 조회·외부 링크 및 이미지 제한은 유지한다.

로컬 모의 응답으로 960·1280·1440·1920px 배치, 16px / 26px 본문, 최대 880px 읽기 폭, 근거 표와 계획 상세 펼치기를 확인했다. 전체 프론트엔드 테스트 792개와 린트·빌드가 통과했다. 실제 운영 데이터 대조는 추가 확인 대상이다. 운영 AI 호출·Action 실행·배포는 수행하지 않았다.

### 3차 적용 범위 — 데이터 연결·연결 규칙

데이터 연결은 원천 이름·유형·접속 확인을 비교하는 목록과 우측 상세로 나눈다. 값이 제공되지 않던 수집 상태·마지막 수집 열 대신 선택한 원천의 수집 이력 안내와 바로 가기를 제공한다. 접속 확인과 수집 실행 상태를 혼용하지 않는다. 접속 정보·수집 대상·표본·매핑·수집 이력과 원천 등록·수정 모달은 공통 입력·표·타이포 기준을 사용한다. 좁은 창에서는 목록과 상세를 위아래로 재배치한다.

연결 규칙은 상태·유형·검색·상세 필터와 적용 조건을 구분하고, 검색어는 ‘검색 적용’ 또는 Enter로 반영한다. 입력만 바꿀 때는 기존 결과·페이지를 유지하고 적용할 때 첫 페이지로 이동한다. 후보 목록과 우측 상세는 흰색 패널과 보라색 선택 표시를 사용한다. 신뢰도는 14px 보조 정보로 표시하며, 검토·반영 상태와 검사 집계를 우선한다. 전체에서 정상 건수를 뺀 값을 임의로 ‘실패’로 표시하지 않는다. 긴 제안 이유·원문은 16px / 26px, 규칙 표·필드·검토 안내는 14px 기준으로 읽는다. 검토 사유·승인 안내를 숨기지 않는다.

`features/sources/sources.css`와 `features/review/rules.css`에서 화면별 스타일을 관리하고, 공통 `workspace.css`의 원천 화면 덮어쓰기와 이전 규칙 화면의 큰 모서리·반투명·그라데이션 스타일을 정리했다. 원천 요청·수집·매핑·분석·검토 결정의 API·권한·충돌 처리·중복 실행 방지·폴링은 유지한다. 실제 운영 데이터 대조, 전체 접근성 및 200% 확대 검토, 운영 배포는 별도 확인 대상이다. 관리자·이력·인증 화면의 후속 적용은 아래 4차 범위에 기록한다.

전체 프론트엔드 테스트 793개와 린트·빌드·변경 파일 포맷 검사가 통과했다. 로컬 모의 데이터로 960·1280·1440·1920px 배치, 원천 매핑, 규칙 근거·검사 결과, 등록 및 비교 모달의 Escape·포커스 복원을 확인했다. 기본 모의 API가 없는 수집 이력·대안 비교는 브라우저에서 404 오류 표시까지만 확인했고, 정상 응답·이동·비교 흐름은 모의 HTTP 자동 테스트로 검증했다. 이는 실제 운영 API 검증을 뜻하지 않는다.

### 4차 적용 범위 — 나머지 관리자·이력·인증 화면

Action 정의와 계정·권한의 목록·등록·상세 및 변경 화면, 실행 이력, 정의 변경·규칙 개정 비교, 제안별 규칙 이력에 같은 기준을 적용했다. 보이는 페이지 제목과 짧은 설명을 제공하고 검색 조건·결과·편집 양식을 구분한다. 관리 폼은 최대 1100px, 계정 폼은 최대 880px로 제한한다. 이력의 실행자·코드·사유·비교 안내는 14px / 21px, 긴 일반 설명 입력은 16px / 26px를 사용한다. 변경 전후 비교와 Action 입력 형식은 공통 표와 영역 내부 가로 스크롤을 사용한다. 이력 종류·개정 선택은 보라색 상태 표시와 `aria-pressed`를 함께 사용한다.

로그인·비밀번호 변경·접근 권한 없음·없는 주소 안내도 흰색 배경, 공통 키컬러·타이포·입력·버튼 기준으로 맞췄다. 로그인 카드의 반투명·그라데이션·큰 모서리·장식 그림자는 정리하고 로그인 왼쪽 장식 오브젝트는 사용자 요청에 따라 표시하지 않으며 소개 문구와 인증 동작은 유지했다. 적용 후 문제 영역의 제목도 화면에 표시한다. 공통 관리 배치는 `components/management.css`에서 관리하며 API·권한·승인·저장·충돌 처리 정책은 변경하지 않는다.

전체 프론트엔드 테스트 793개와 린트·빌드를 통과했다. 로컬 모의 데이터로 관리자 목록·편집 폼, 실행 상세, 정의 변경 목록·규칙 개정 비교, 제안 이력, 로그인·비밀번호 변경의 배치를 확인했다. 기본 1280px 창과 추가 960·1440·1920px 창에서 관리 화면의 배치·폼 최대 폭을 점검했다. 실제 비밀번호 변경·권한 변경·Action 등록과 운영 배포는 수행하지 않았다. 운영 연동·실제 장문 데이터·200% 확대·보조 기술 검증은 별도 확인 대상이다. 기존 빌드의 500kB 초과 청크 경고는 남아 있다.

### 최신 develop 통합

최신 develop에 추가된 로고의 업무 데이터 이동 링크와 실제 수집 요약 기능을 보존했다. 원천 비교 목록은 이름·유형·접속 확인을 유지하며, 선택 원천의 최근 전체 읽기 상태·종료 시각·CDC 마지막 반영 시각은 우측 상세 상단의 표로 확인한다. 수집 요약의 새로고침·권한 오류·진행 중 폴링과 전체 수집 이력 경로는 유지한다. 수집 성공 시각과 실패 실행 종료 시각·CDC 상태의 의미를 구분하는 안내를 함께 제공한다.

독립 리뷰에서 발견한 페이지 축소 회귀는 사용자 승인 후 수정했다. 마지막 페이지가 사라지거나 0건이 되면 실제 부모 조회 페이지도 유효 범위로 이동하고, 조회 중에는 보정을 미룬다. 문제 상태 변경으로 21건에서 20건이 되는 흐름의 재조회 회귀 테스트를 추가했다.

통합 검증에서는 전체 52개 파일·808개 테스트 중 수집 바로 가기 테스트 1개가 요약 요청과 이력 요청을 구분하지 않아 실패했다(807개 통과). 요약(size=1)과 전체 이력(size=20)을 구분하도록 테스트를 맞춘 후 수집 화면 20개가 모두 통과했다. 페이지네이션·문제 상태 변경 회귀 20개, 최종 빌드·린트·변경 파일 포맷·diff 공백 검사도 통과했다. 별도 마스코트 파일·테스트와 로컬 백엔드 연결 설정은 커밋 범위에서 제외했다.

### 후속 develop 충돌 통합

최신 develop의 감사 이력 상세·변경 전후 분리 조회를 사용하고 상세 영역의 공통 가독성 스타일을 유지한다. 연결 규칙 상단의 수동 검사·실행 목록 이동, 검토 상태 안에서의 기본 유형 선택·집계·검색 대상 제한, 원천 등록 직접 진입과 닫기 시 URL 정리를 보존했다. 후보 검색은 기존의 명시적 검색 적용을 유지하며 100건씩 받는 서버 목록과 20건 단위 화면 이동을 구분해 검증한다.

충돌 통합 최종 상태에서 전체 프론트 테스트 56개 파일·878개와 빌드·린트·변경 파일 포맷·diff 공백 검사가 통과했다. 독립 재리뷰에서 남은 Critical·Major·Minor는 없었다. 이는 로컬 모의 API 검증이며 운영 배포·연동 검증을 뜻하지 않는다.

### 개선 후 확인

긴 영문 그래프 이름의 줄바꿈 보완은 로컬 모의 데이터로 확인했다. 공백 없는 영문 객체명·유형명이 14px 글자 크기를 유지하며 노드 안에서 여러 줄로 표시되고, 가로 넘침 없이 선택할 수 있음을 확인했다. 관련 업무 데이터·관계 배치 회귀 테스트 70개를 통과했다. 실제 운영 데이터 전체의 길이·관계 수 검증은 별도 확인 대상이다.

- [ ] 확정된 라이트·키컬러·기본형·우측 상세·데스크톱 방향을 반영했다.
- [ ] 보이는 페이지 제목과 일관된 메뉴를 제공한다.
- [ ] 목록 비교·상세 근거·중요 상태를 불필요한 왕복 없이 찾을 수 있다.
- [ ] 실제 긴 데이터로 표 정렬·원문 확인·관계도 라벨·상세 읽기 폭을 확인했다.
- [ ] 타이포·대비·간격·선택·포커스가 구분되고 반복 설명이 정리됐다.
- [ ] 검색 적용·초기화·페이지 경계·0건·1쪽·처리 중 동작을 확인했다.
- [ ] AI 설명·근거·신뢰도·실행 결과와 재시도 정책을 구분했다.
- [ ] 창 너비·200% 확대·키보드·다이얼로그 포커스·역할별 노출을 확인했다.
- [ ] 기존 기능 영향과 변경 범위의 검사·테스트·빌드 결과를 기록했다.

이 체크리스트는 **전체 개선 범위의 수용 검토**에 사용한다. 화면 구현 완료만으로 운영 데이터·접근성 항목까지 완료 처리하지 않는다. 기존 배포 관찰은 2절이며 새 UI의 운영 검증 결과를 뜻하지 않는다. 수용 검토는 `항목 찾기 → 핵심 값 비교 → 상세 근거 확인 → 다음 행동 판단` 순서로 기록한다.

남은 수용 검토는 별도 폰트 로딩, 실제 운영 데이터·상태별 대비 및 브라우저 200% 확대·보조 기술 검증이다. 2절 배포 관찰에서 확인한 정의 변경 이력의 조회 오류는 운영 API에서 재확인이 필요하며, 로컬 모의 응답의 정상 표시는 그 오류의 해결을 뜻하지 않는다. 확정 방향을 다시 결정할 필요는 없으며 기존 명세로 판단할 수 없는 업무 변경만 담당자에게 확인한다.
