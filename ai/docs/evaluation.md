# AI 제안 평가

- 이슈: S15P31C106-20 · 담당: 김서연 · 검토: 정유림 · 상태: 초안
- 평가 데이터와 정답은 [dataset.md](dataset.md). 앞부분은 평가 기준, 뒤쪽 '평가 결과'는 실행한 순서대로 적은 결과다.

## 0. 평가 대상

추가 답변 Q4(객체 유형 분석·관계 구조 제안·정합성 검증), Q6(연결 규칙), 팀 결정(비정형 추출 필수)을 모두 평가한다.

| 평가 대상 | 무엇을 비교하나 | 정답 파일 |
| --- | --- | --- |
| 객체 유형 분석 | AI 객체 유형·속성 후보 ↔ 정답 객체 유형·속성 | `ontology.json` |
| 관계 구조 제안 | AI 관계 후보(방향·연결 컬럼) ↔ 정답 관계 | `ontology.json` |
| 연결 규칙 발견 | AI 연결 규칙을 값에 적용한 결과 ↔ 정답 값 단위 연결 | `mapping_rules.json`, `id_links.json` |
| 정합성 검증 | AI가 제안한 규칙으로 서버가 시험 적용(FN-CHK-04)한 결과의 미연결·중복·조건 위반 ↔ 정답 정합성 결과 | `integrity_checks.json`, `integrity_issues.json` |
| 비정형 추출 | AI 추출 개체·부정/추정·설비 연결 ↔ 정답 주석 | `note_annotations.json` |

- **정합성 검증**은 검사를 실행하는 쪽이 Backend(FN-CHK·FN-ISS)다. 그래서 "AI가 낸 규칙이 정합성 문제를 정답만큼 정확히 드러내는가"로 평가한다. 정답과 같은 문제를 찾으면 맞음, 정상 결측을 문제로 보면 오탐으로 센다.
- **개별 데이터 연결은 보조 지표로 포함한다.** 규칙이 맞아도 값 하나하나가 맞게 이어져야 Agent 답이 맞기 때문이다(Q4는 선택 사항). 다만 Req. 27 정확도의 분모에는 넣지 않는다. 값 수가 규칙 수보다 훨씬 많아 지표가 값 단위 결과에 끌려가기 때문이다. 보고 지표는 값 연결 일치율 = 정답과 결과가 같은 값 ÷ 정답 값이다. 결과는 연결됨·미연결·보류로 나눈다.


## 0-1. 평가 데이터 종류 (10-26 외부 리뷰(GPT) 반영, 11-04 B2 추가)

데이터·정답·분석기를 같은 사람이 만들면 점수가 실제보다 좋게 나온다. 그래서 결과를 데이터 종류별로 따로 보고한다.

| 데이터 | 만드는 사람·방법 | 확인하는 것 | 상태 |
| --- | --- | --- | --- |
| A 개발용 | 김서연, 생성기 (`data/data-v1.0`) | 기능 오류. 분석 기준값도 이 데이터를 보며 정했다 | 있음 |
| B 독립 | 분석기 코드·A·C 데이터를 보지 않은 별도 에이전트가 명세만 보고 설계 (`data/data-b-v1`, 정답 `data/gold-b-v1`). 사출 공장 표 6개, 관계 6 · 미끼 2 | 처음 보는 구조에서도 관계를 찾는지 | 있음 (평가 후 고침, 고친 뒤 수치는 낙관적) |
| B2 독립 | B와 같은 방식, 다른 에이전트 (`data/data-b2-v1`, 정답 `data/gold-b2-v1`). PCB 조립 공장 표 8개, 관계 9(시스템 간 3) · 미끼 3 | B를 보고 고친 뒤에도 처음 보는 구조에서 맞는지 | 있음 (평가 후 고침, 고친 뒤 수치는 낙관적) |
| C 스트레스 | 김서연, A를 변형 (`app/dataset/stress.py`). **분석기를 고정한 뒤** 만들고 결과를 보고 분석기를 고치지 않는다 | 다른 표기, 잡음, 우연히 숫자가 겹치는 미끼 컬럼을 견디는지 | 있음 |

- 같은 생성기에서 행만 다시 뽑는 것은 독립 평가가 아니다(컬럼·식별자 형식·규칙을 공유).
- B·C 결과가 나빠도 평가 데이터를 고치지 않는다. 원인은 따로 기록하고, 분석기를 고친 뒤 결과는 "고친 뒤"로 따로 적는다.
- 발표 자료의 정형 분석 수치는 A·B·C를 나란히 적는다. A만 단독으로 쓰지 않는다.

## 2. 신뢰도 산정 방식

### 2-1. 방식 비교

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| LLM이 스스로 말한 확신도 | 구현이 쉬움 | 근거가 없고 같은 입력에도 값이 흔들림. 높게 말하는 경향 | **사용하지 않음** |
| **근거 신호 점수 합산** | 왜 그 점수인지 항목별로 보여 줄 수 있음 (S04 점수 내역) | 가중치를 사람이 정해야 함 | **기본 방식** |
| 반복 일치도 | LLM 결과의 흔들림을 숫자로 잡음 | 호출 횟수만큼 비용 증가 | LLM이 만든 후보에만 **신호 하나로 포함** |
| 정답셋 보정 | 점수와 실제 정답률을 맞출 수 있음 | 정답셋이 있어야 함 | 평가 단계에서 **가중치·구간 조정**에 사용 |

### 2-2. 결정(안)

- 신뢰도 = 후보 종류별 근거 신호 점수의 합. 범위 **0~1** (운영 ERD `proposal_item.ai_confidence`, 와이어프레임 표기와 같음).
- **의미:** "확인된 근거가 얼마나 강한가"를 나타내는 점수다. **맞을 확률이 아니다.** 화면에도 "확률"이라고 쓰지 않는다.
- **구간(초기값):** 높음 0.8 이상 · 보통 0.5~0.79 · 낮음 0.5 미만. 정답셋 평가 후 구간별 실제 정답률을 보고 조정한다.
- **화면 표시:** `점수 · 구간 · 점수 내역` (예: `0.75 · 보통 · 형식 유사 0.35 + 이름·주석 의미 0.25 + 적용 가능 비율 0.15`)
- **AI 신뢰도와 시험 매칭률은 따로 표시한다**(FN-CHK-05). 시험 매칭률은 Backend의 규칙 시험 적용(FN-CHK-04) 결과이므로 AI 신뢰도에 넣지 않는다.
- 신뢰도를 계산하지 못한 후보는 값 없음으로 두고 0으로 표시하지 않는다.
- **같은 근거를 두 번 더하지 않는다.** 한 번의 값 비교에서 나온 신호(값 포함 비율, 형식 유사도, 적용 가능 비율 등)는 한 묶음으로 보고, 묶음 안에서는 가장 큰 신호 하나만 더한다. 묶음: ① 값 비교 ② 이름·주석 의미(LLM) ③ 구조(키·개수 관계) ④ 반복 일치도.
- **치명적 문제가 있으면 점수 상한을 둔다.** 근거를 원본에서 다시 찾지 못함, 변환 뒤 서로 다른 도착 값이 하나로 합쳐짐, 일대일이어야 하는데 여러 개로 이어짐 → 최대 0.49(낮음). 점수 내역에 이유를 적는다.
- **LLM 판단은 점수에 더하지 않는다** (10-27 외부 리뷰(GPT) 반영). `llm_judgement`에 따로 적고, LLM이 '업무상 맞지 않다'고 할 때만 보류·상한을 건다. LLM 동의만으로 점수가 오르면 데이터 근거 없이 최고점이 될 수 있기 때문이다. 10-28에 컬럼 이름 근거(+0.1)를 더해 관계 점수는 최대 0.8이다. 값 포함·도착 키·이름 근거가 모두 있어야 '높음'이 된다.
- **보정:** 평가 때 구간별 실제 정답률을 A·B·C 데이터마다 따로 계산한다. "높음인데 틀린 후보"를 먼저 하나씩 원인 분석한다. 정교한 확률 보정 모델은 만들지 않는다(6주 범위).
### 2-3. 후보 종류별 신호와 배점 (초기값)

| 후보 | 신호 (최대 점수) |
| --- | --- |
| Object 유형 | 기본키가 있음 (0.25) · 다른 표가 이 표의 키를 가리킴 (0.25) · 표 이름·주석의 의미 (0.2, LLM) · 고유 값 비율 (0.15) · 반복 일치도 (0.15) |
| Property | 값 형식과 자료형이 맞음 (0.35) · 결측률 (0.15) · 컬럼 이름·주석의 의미 (0.3, LLM) · 반복 일치도 (0.2) |
| Link 유형 | 값 포함 비율 (출발 값이 도착 키에 있는 비율) (0.4) · 자료형·형식 일치 (0.2) · 이름·주석 유사 (0.2) · 개수 관계 확인 (0.2) |
| 연결 규칙 | 형식 유사도 (0.45) · 컬럼 이름·주석의 의미 (0.3, LLM) · 적용 가능 비율 (빈 값 제외) (0.25) — 시험 매칭률은 넣지 않음 (서버 값) |
| 문서 연결 (메모 → 객체) | 정식 이름·별칭 사전 일치 (0.4) · 문맥 일치 (라인·작성자 소속) (0.2) · 반복 일치도 (0.2) · 원문 위치 확인 (0.2) |

반복 일치도는 LLM을 같은 입력으로 여러 번 부르는 방식이라, GMS 예산(제안기 하루 약 60회)을 고려해 저장해 둔 응답을 재사용하고 평가 실험에서만 반복한다.

정합성 검사와 문제 판정은 Backend 기능(FN-CHK·FN-ISS)이다. 그래서 신뢰도 계산에는 넣지 않고, 평가는 0절 '정합성 검증' 방식으로 한다.

## 3. 제안 이유·근거와 표시 규칙

FN-AIP-05: 근거는 원천 테이블·컬럼·값이나 문서 원문이고, **근거 종류를 나누기보다 제안 이유를 충분히 설명하는 데 집중**한다. 그래서 후보마다 **제안 이유**(왜 이 후보를 제안했는지 쓴 설명문)를 반드시 붙이고, 근거는 그 설명을 뒷받침하는 원천 위치로 붙인다.

| 근거 | 표시 형식 | 원본 재확인 방법 (Req. 12) |
| --- | --- | --- |
| 원천 테이블·컬럼 | `mes.work_order.order_ref · varchar(20) · 주석 "주문 참조 번호"` | 원천에 해당 표·컬럼이 실제로 있는지 |
| 원천 값 | `표본 2608012, 2608031 · 결측 2.7% · 고유 146` | 해당 값이 실제 그 컬럼에 있는지 |
| 문서 원문 | `[HN-260814-N 38~48] "1라인 3호 프레스"` | 그 위치에 그 글자가 정확히 있는지 |

- 규칙을 실제 데이터에 적용한 결과(시험 매칭률·정상 연결·미연결·중복·조건 위반)는 Backend 검사(FN-CHK-04·05)가 만들어 따로 보여 준다. AI 제안의 근거에 넣지 않는다.
- 원문은 **고치지 않고 그대로** 인용하고, 문서 ID와 위치를 함께 표시한다.
- 개인정보 컬럼(이름 등)의 샘플 값은 가려서 표시하고, LLM에도 보내지 않는다.
- 후보 하나에 근거는 최소 1개, 화면에는 최대 3개를 보여 주고 나머지는 "더 보기"로 둔다.

## 4. 근거가 확인되지 않은 후보의 처리 (Req. 12)

1. 후보를 만든 뒤, 모든 근거를 3절의 "확인 방법"으로 **원본에서 다시 확인**한다. (LLM이 만든 근거도 예외 없음)
2. 확인되지 않은 근거는 **삭제**하고, 화면에 근거로 표시하지 않는다.
3. 확인된 근거가 하나도 남지 않은 후보는 **Backend로 보내지 않는다.** 실행 기록에만 남긴다.
4. 이런 후보 수는 보조 지표 "근거 미확인 비율"(= 근거 미확인으로 제외된 후보 ÷ 생성된 전체 후보)로 보고한다.

[결정 필요] 3번 대신 "근거 미확인" 사유로 **보류**해서 관리자에게 보여 주는 방법도 있다. Req. 12의 "확인되지 않은 내용을 근거로 표시하지 않는다"에는 3번이 더 맞다고 판단해 3번을 제안한다.

## 5. '정답과 일치' 판정 기준

- 이름(code·name)은 판정에 쓰지 않는다. AI가 붙인 이름이 달라도 **같은 원천을 같은 방향으로 가리키면** 맞은 것으로 본다. 이름은 참고로만 보고한다.
- 정답 하나에는 후보 하나만 짝짓는다. 같은 정답을 가리키는 두 번째 후보는 **중복 후보로 오답** 처리한다.
- 정답셋에서 `acceptable`인 항목과 맞으면 정답으로 인정하되, 못 찾아도 재현율에서 빼지 않는다.
- 엄격 기준과 완화 기준 두 가지로 계산하고, **주 지표는 엄격 기준**으로 한다.

| 대상 | 엄격 기준 (주 지표) | 완화 기준 (참고) |
| --- | --- | --- |
| **Object** | 후보의 원천 표 집합 = 정답 `source_tables` | 원천 표가 하나 이상 겹침 |
| **Property** | 소속 Object가 정답과 짝지어짐 + 원천 컬럼 = 정답 `source_column` + `data_type` 같음 | 자료형은 달라도 됨 |
| **Link** | 출발·도착 Object가 정답과 짝지어짐 + **방향 같음** + `via` 컬럼 같음 (메모 관계는 유형 쌍이 같음). `cardinality`는 따로 "개수 정확도"로 채점 | 방향이 반대여도 인정 |
| **식별자 연결 규칙** | 출발·도착 컬럼 같음 + 규칙 유형 같음 + `id_links.json`의 모든 값에서 **결과가 같음** (연결 대상, 미매칭, 보류) | 값 결과 일치율 95% 이상 |
| **메모 추출 (개체)** | 유형 같음 + 원문 위치 정확히 같음 + 연결 결과 같음 (모호하면 보류하고 정답 후보를 모두 포함) | 위치가 절반 이상 겹침 |
| **메모 추출 (관계)** | 관계 유형 같음 + 양 끝 개체가 각각 정답과 짝지어짐 | — |

- 메모 추출 개체는 **부정·추정 표시**도 정답과 같아야 한다(FN-AIP-02). 예: 정답이 "부정"인 관찰을 "확정"으로 추출하면 오답.
- 식별자 연결 규칙은 변환식을 글자 그대로 비교하지 않는다. AI가 다른 방식으로 써도 **같은 값에 같은 결과**를 내면 정답이다. 평가 스크립트가 규칙을 직접 적용해 보려면 규칙이 실행 가능한 형식이어야 하며, 형식은 FN-CHK-04·FN-REV-02와 같은 규칙 문법으로 맞춘다(미정).

## 6. 평가 범위와 집계 단위

- **평가 대상 후보:** 한 번의 실행에서 Backend로 보낸 후보 중 상태가 `proposed`(승인 요청)인 것.
- **보류(`held`) 후보:** 정확도 분모에서 빼고, "보류 판정 정확도"(정답에서도 `ambiguous`·미매칭인 것을 보류한 비율)로 따로 본다.
- [결정 필요] Req. 27의 "전체 평가 후보"에 보류 후보도 넣을지. 위 안은 넣지 않는 쪽이다.
- **집계 단위:**
  - 후보 종류별: Object / Property / Link / 식별자 연결 규칙 (+ 메모 추출, 정합성 이슈는 별도 표)
  - 전체: 모든 종류를 합친 정답 수 ÷ 모든 평가 후보 수
  - 원천별, 실험 조건별(A 스키마만 / B + 샘플 / C + 메모 / D + 개선 프롬프트)
- **승인 수용률:** 후보 종류별, 실행별로 계산. Backend에서 받을 기록: `candidate_id`, `run_id`, 결정(승인·거절·보류), 결정 시각, 사유, 수정 여부.
- [결정 필요] 관리자가 **고쳐서 승인한** 후보를 승인으로 셀지, "수정 승인"으로 따로 셀지.

## 7-1. 과거 데이터 기반 추론 평가 (추가 답변 Q5)

AI가 앞서 승인·거절된 결과를 참고해 더 나은 제안을 하는지 본다.

| 단계 | 방법 |
| --- | --- |
| 1. 첫 실행 | 데이터 일부(예: ERP 표만)로 제안 → 정답셋 기준으로 승인·거절을 기록 (사람 대신 정답셋으로 판정해 재현 가능하게) |
| 2. 비교 실행 | 나머지 데이터로 두 번 실행: **A** 과거 결정 없이 / **B** 1단계 승인·거절 결과(요약)를 함께 제공 |
| 3. 비교 지표 | A·B의 정확도, 거절된 것과 같은 후보를 다시 낸 비율(재제안률), 승인된 규칙을 다시 쓴 비율(재사용률) |
